# 缩略图生成调研与优化策略

本页讨论进度条预览的离线生成，不讨论影片海报选图。调研核对日期为 2026-10-22；两轮本地优化均已通过整片验收，第二轮证据于 2026-10-23 完成独立核对。现行实现见[播放链路](../developer/playback.md)。

建议保留普通影片的快速采样，先对 Dolby Vision P5 比较「现行逐点恢复」「有界区段连续抽帧」「整片单遍连续抽帧」。依据实际开销决定切换条件，避免把继续增加预读长度作为主要优化方向。

## 主流方案与适用范围

| 产品或工具 | 一手资料能确认的方案 | 对本项目的意义 |
| --- | --- | --- |
| Jellyfin v12.2 | 每种目标宽度一次 FFmpeg 连续输出 JPEG 序列，再生成 sprite | 离线批量抽帧的直接参考；不等于所有片源都应从头完整解码 |
| Plex | BIF 预览索引；默认两秒间隔，并提供仅关键帧配置 | 关键帧近似是常见性能取舍；闭源内部恢复算法无法确认 |
| Emby | 官方论坛的一手运行日志展示单个批量图片序列任务，使用专用抽取参数 | 支持批量生成这一方向；案例不能代表所有版本和编码 |
| Mux | storyboard 精灵图加 WebVTT／JSON 时间与坐标索引 | 展示协议与解码策略可以独立演进；密度属于产品选择 |
| mpv thumbfast | 持久子播放器通过 IPC 按悬停位置 seek，先快速后精确 | 适合按需交互，不直接替代 NAS 的整片预生成 |
| Apple HLS／AWS MediaPackage | 预先生成 I-frame trickplay 轨道，或交付 JPEG 图片播放列表 | 适合已有转码流水线；更换索引格式本身不解决原片取帧问题 |

Jellyfin 的结论核对到 v12.2、提交 `ca0f16eb7c195f720a1493ed469a27c4657db0c6`：[抽取命令](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs#L927)、[抽取后生成拼图](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/Jellyfin.Server.Implementations/Trickplay/TrickplayManager.cs#L435)。其[关键帧配置](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/MediaBrowser.Model/Configuration/TrickplayOptions.cs)与普通解码分开，不能把关键帧路线当作完整元数据保证。

Plex 的依据为[预览索引用途](https://support.plex.tv/articles/201725267-what-are-video-preview-thumbnails-in-plex/)和[官方隐藏参数](https://support.plex.tv/articles/201105343-advanced-hidden-server-settings/)。Emby 的依据为[章节图与时间间隔配置讨论](https://emby.media/community/topic/121601-how-to-get-the-video-preview-thumbnail/)及[官方论坛的抽取日志](https://emby.media/community/topic/145118-video-slider-not-working/)；日志里的 `-skip_interval` 不作为通用 FFmpeg 参数引入本项目。

Mux 的[storyboard 文档](https://www.mux.com/docs/guides/create-timeline-hover-previews)说明图片格与时间范围的对应关系；这不公开其内部解码算法。thumbfast 的[源码与说明](https://github.com/po5/thumbfast)核对于上述日期，不代表服务端批处理方案。Apple 的[trickplay 要求](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html#trick-play)和 AWS 的[图片播放列表说明](https://docs.aws.amazon.com/mediapackage/latest/ug/trick-play.html)用于区分交付形式，不用于推断 NAS 抽帧速度。

## 异常情况如何处理

### 定位失败与关键帧不兼容

mpv 提供提前定位再解码的[预读偏移选项](https://mpv.io/manual/stable/#options-hr-seek-demuxer-offset)，用于绕过部分解复用器的晚定位问题，同时明确存在额外解码成本。这支持有界预读作为恢复方法，不支持把 120 秒视为行业通用值。

Jellyfin 在关键帧抽取报错后[回退常规抽取](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs#L857)。本项目应继续区分关键帧近似与正确完整解码；缺图、错时间或不兼容时只修补相应位置，不能将任意后续帧挤入缺失槽位。

thumbfast 作者报告的[末尾 GOP seek 无帧问题](https://github.com/po5/thumbfast/issues/132)说明高性能工具同样有边界情况；该问题记录不证明本片具有相同根因，也不构成可直接替换的解决方案。

### Dolby Vision 元数据恢复

本片已验证的事实是：4980 秒附近随机定位后无法取得有效杜比元数据，60 秒预读仍无合格输出，90 秒与 120 秒预读均能恢复目标画面。**此前的「长 RPU 引用」属于工作假设，具体位流原因尚未证实。**

[Dolby 官方 Profile 表](https://ott.dolby.com/OnDelKits/Dolby_Vision_Online_Delivery_Kit/v1/Documentation/Specs/Visio_Profiles/help_files/topics/c_dovi_profiles_public.html#concept_th5_d2l_1v__entry__1)将 P5 的 metadata compression 列为 None，CCID 0 也没有普通 SDR／HDR10 兼容基底。不能把本例泛化为所有规范 P5 都需要长距离引用恢复。

FFmpeg n7.1.5 的[解析检查](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/dovi_rpudec.c#L519-L553)区分多种错误，而 HEVC 层的[通用警告](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/hevc/hevcdec.c#L3665-L3670)不能说明是哪一种。非规范编码、解析器兼容性和状态缺失仍需逐帧 RPU 调查才能区分；合成引用测试不能充当实片根因证据。

优化必须复用连续解码过程中的真实状态。[HEVC flush](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/hevc/hevcdec.c#L4050-L4060)会调用[杜比上下文清理](https://github.com/FFmpeg/FFmpeg/blob/n7.1.5/libavcodec/dovi_rpu.c#L42-L55)。仅保持进程存活、每个目标仍重新 seek，不能保证保留这些状态。

### 错色、损坏尾部与失控任务

| 情况 | 优化方案必须保留的处理 |
| --- | --- |
| 硬解成功但缺少杜比 side data | 验证实际元数据和颜色，失败回到已验证的软件路径 |
| 视频流之外还有附带封面 | 显式映射真实视频流，保留真实视频时长判断 |
| VFR、乱序或重复 PTS | 每格按真实 PTS 配对，校验数量与编号；不靠输出文件序号猜时间 |
| 中间某格缺少合格帧 | 留作修补或报错；禁止用 `fps` 的复制帧掩盖缺失 |
| 片尾确实损坏或无视频 | 保留完整页与失败原因，沿用显式手动接纳流程 |
| 程序仍运行却不产出 | 分别监控解码推进和合格样本推进，并设硬上限与清理 |
| 暂存目录不可写或空间不足 | 昂贵抽取前检查；暂存量持续有界 |

硬件路径丢元数据导致错色已有 [mpv 官方问题记录](https://github.com/mpv-player/mpv/issues/10287)，但该设备案例不用于判定当前 NAS 的能力。[libplacebo 的杜比处理](https://ffmpeg.org/ffmpeg-filters.html#libplacebo)依赖输入帧元数据，因此不能通过丢掉 RPU、按普通 HDR／SDR 处理来宣告成功。

Jellyfin 的[进展监控](https://github.com/jellyfin/jellyfin/blob/ca0f16eb7c195f720a1493ed469a27c4657db0c6/MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs#L979)以新图片是否持续出现判断响应性。本项目需要额外允许预读阶段尚无样本的合理时间，同时限制输入跨度、解码工作量、暂存图片数量和总时间，避免错误时长或持续无效元数据造成无界任务。

## 本项目的优化策略

### 先建立三路可比较的基准

2026-10-22 的隔离诊断使用 2 CPU、2 GiB 内存、零 swap。两轮生成合计 841 次受控命令、约 104.15 分钟，其中 349 次定位命令未产生过滤后的时间戳输出，合计约 30.12 分钟。22 页拼图合计约 3.48 秒。

这些数据包含失败以及未提交页重做，**不是修复后单次完整生成基准**。有输出但因 PTS 不合格而丢弃的成本尚未单列；进程与滤镜初始化也包含在抽帧命令耗时内，不能据此排除。原始数据位于本机忽略目录 `output/diagnostics/northeast-preview-20261022/`。

| 候选 | 要验证的收益 | 主要代价与边界 |
| --- | --- | --- |
| A：现行逐点与短窗口 | 保留普通位置低成本定位，作为同版本对照 | 困难位置存在重复预读和逐档试错 |
| B：整片单遍连续解码 | 减少重叠解码并持续保留状态 | 必须解码完整 4K 时间轴；中断后重建状态成本较高 |
| C：自适应区段连续解码 | 在困难区段摊薄一次恢复，保留普通片快路径 | 区段入口需验证；过短仍重复、过长增加让行与恢复成本 |

初步优先评估 C，同时把 B 作为 P5 的必要对照。若某片持续恢复的总成本接近顺序解码成本，可选择 B；不根据扩展名或单次失败让全部影片强制走全片扫描。窗口点数、跨度和切换阈值由测量决定。

### 连续解码与逐页提交分开

候选架构让解码器在区段内持续向前读取，仅把符合采样目标、时间和元数据要求的帧送往现有色彩转换。页面收集器持续校验并提交完整页，及时删除中间图；跨过一张 sprite 页不必销毁解码器，也不把整片所有图片放入内存。

`fps`／`select` 处于[解码后的过滤阶段](https://ffmpeg.org/ffmpeg.html#Detailed-description)，降低输出帧率不等于跳过所有中间帧的解码。时间选帧放在昂贵转换之前的思路可借鉴，但必须保留本项目对缺元数据、缺格及真实 PTS 的验证，不能直接复制其他工具的命令当作完成实现。

中断或播放让行后，已经提交的页面保留。进程终止意味着解码状态丢失；恢复时需要重新验证解码入口，必要时扩大一次性预读或回退从头重建，不能把「最后一张图的时间」当成可序列化的 decoder checkpoint。应把恢复成本计入候选方案对照。

### 恢复按原因分流并限制重复工作

- 将无输出、时间错位、元数据解析异常、硬件能力、资源与输入错误分开记录；通用杜比警告只作为线索，不假装已分类根因。
- 只有经实测恢复的入口才能在有限相邻区段使用；按片源身份、FFmpeg／解码配置失效，离开区段后重新探测普通路径。
- 同一轮恢复计划内，对目标集合、解码配置、实际起点和输入跨度均相同的等价尝试去重；成功恢复后优先在同一连续解码区段取得后续目标。
- 资源错误、取消和播放让行直接传播；不能扩大重试链来吞掉这些状态。
- 120 秒单点恢复继续作为受控兼容回退，不继续逐级增加长度作为常规提速手段。

### 后续候选与暂不采用的捷径

硬件解码与 GPU 色彩转换作为独立候选，先验证 Main10、杜比 side data、输入格式和像素结果。FFmpeg 升级可纳入隔离对照，但当前没有证据证明升级自动解决本片。

仅对反复失败或反复重建的文件评估「已验证解码入口与恢复范围」缓存。[dovi_tool](https://github.com/quietvoid/dovi_tool#extract-rpu)可辅助调查位流；关键帧、scene refresh 或存在 RPU NAL 都不能单独证明入口可恢复。默认给全部影片增加一次位流全扫描，还会引入 I/O 和维护成本。

本阶段保持现有 480×270、10 秒采样、单次最终 JPEG 编码和客户端协议。减少图片数量、降低画质、更换为按需服务或先生成完整 SDR 代理文件都不是当前性能验收的替代方案。普通 SDR／HDR 继续保留现行快速路径，不将本次 P5 问题扩为全格式重写。

## 本地初版与验证进展

初版采用 C 的逐页有界区段，沿用现有进程取消和整页原子提交。一次单点恢复成功后，下一个目标仍先直接定位；只有这个目标也无法取得合格画面，才从刚才验证成功的确切起点连续解码。这样既能减少连续异常位置的重复恢复，也能避免孤立异常点让后续正常位置承担多余预读。

短预读入口先限制为最多 6 格，较长预读入口最多 25 格，并按剩余页面及输入跨度裁剪；入口只用一次。区段返回经过图片、编号、元数据和真实 PTS 校验的连续前缀，随后继续探测首个未覆盖目标。具体上限与回退行为统一见[播放链路](../developer/playback.md#倍速缩略图与预缓存)。

跨页持久解码、解码推进与样本推进的独立监控、整片 B 自动选路尚未接入。先用现有页面边界限制一次工作的范围，避免在缺少性能证据时同时改写进程和提交协议。没有更改采样密度、像素合同、缓存修订或客户端协议。

隔离真实片段使用当前容器镜像、固定源码快照、2 CPU、2 GiB 内存和零 swap；每次使用全新临时产物。操作系统文件缓存未强制清空，以下结果只描述本机受限环境，不外推 NAS。

| 《东北警察故事2》采样片段 | 现行 A | 自适应初版 P | 当前结论 |
| --- | --- | --- | --- |
| 100～150 秒，6 格，两轮 | 6.041／6.828 秒 | 6.449／6.977 秒 | 均为 7 条命令、相同 PTS，逐像素一致；耗时范围相近 |
| 530～590 秒，7 格，两轮 | 82.353／87.408 秒 | 63.096／60.894 秒 | 平均耗时减少约 27%；及时回到直接定位，减少不必要的旧共享窗口 |
| 610～740 秒，14 格 | 168.881 秒 | 103.413 秒 | 耗时减少约 39%，使用一次连续区段 |
| 1650～1670 秒，3 格 | 74.400 秒 | 74.746 秒 | 同为 12 条命令，孤立恢复未使后续正常位置强制连续解码 |
| 4980～5000 秒，3 格 | 269.026 秒、22 条命令 | 162.594 秒、10 条命令 | 包括寻找入口的完整恢复链，耗时减少约 40%；相同 PTS、逐像素一致 |

预先指定 4860 秒入口的 C 原型取得 4980～5000 秒三格耗时 53.705 秒，未计寻找入口的成本，不能将其相对 A 的倍数作为实际策略提速。该原型与 A／P 的相同时间图片最大 RGB 差异为 1/255，符合量化抖动量级；生产转换参数保持原值。原始命令、资源计数、实际 PTS、文件哈希及可重复像素检查位于本机忽略目录 `output/diagnostics/preview-optimization-20261022/`。

B 的相同 10 秒密度观测在 0～240 秒连续输出 25 格，耗时 102.970 秒；另一次 20 秒密度的 0～300 秒吞吐观测为 129.770 秒。两者都需要持续解码中间的 4K 帧，仅为顺序解码成本观测，未覆盖 B 的整片恢复、跨页提交和整体性能，不能据此声称整片 B 优于或劣于 C。

资源复核将最终输入上限从原型的 372 秒收紧为 300 秒，保留全部区段的两倍输入时长预算及 600 秒执行上限，避免较慢 CPU 的预算比例缩水。上述 P 小段实际连续窗口只有 62 秒、142 秒，未受这次收紧影响；整片测试使用最终 300 秒上限的冻结代码。

### 整片验收结果

最终代码从空诊断缓存单次生成《东北警察故事2》全部 540 格、22 页，耗时 **3840.495 秒（64 分 0.5 秒）**；包含恢复尝试及最终拼图。1650 秒、4980 秒及片尾均通过，未手动接纳缺失。该结果是本机受限环境的一次完整运行，不与包含失败和续跑的历史 104.15 分钟直接计算提速比例。

540 格均通过实际 PTS、图片及杜比元数据过滤链核对，时间严格递增，偏移范围为 −0.25～+9.875 秒，符合既有单点容差；连续区段仍采用更严格的两秒范围。334 格来自单点路径、194 格来自 31 次连续区段、12 格来自旧短窗口，最长连续输入为 272 秒。22 张 JPEG 均独立严格解码为 2400×1350；隔离 ASGI 请求实际图片处理函数，全部返回 200、`image/jpeg` 且字节哈希一致。该交付检查不扩大为真实服务认证和清单查询验收，后两者另有回归覆盖。

生成阶段执行 731 条命令，均正常结束。248 次定位未得到过滤后的时间戳，合计 788.412 秒，约占命令耗时的 20.5%；进一步减少入口试错仍有价值。容器保持 2 CPU、2 GiB 内存、零 swap，内存计数曾达到 2 GiB 上限并触发回收，未发生 OOM。该计数包含文件缓存，不能当作进程私有内存，也不能据此宣称有充足余量。

整片生成完成后，诊断脚本因日志参数重名退出，原退出码 1 和失败记录保留。随后单独使用同镜像、同资源限制的只读容器完成上述后验检查，退出码 0；未重跑抽帧或修改成品。证据包括 `F-candidate-final.jsonl`、`F-candidate-final-post-verification.json`、补充的 300 秒边界核对及 `verification-summary.json`，均位于上述本机诊断目录。本地服务健康、既有 22 页缓存与清单哈希未变；本次产物保持隔离，未部署 NAS。

## 第二轮：成本自适应与恢复提示

第二轮对照中的 A 是上面已验收的第一轮最终代码，P 是本轮候选；不能将两轮的 A 混为同一实现。仍使用相同镜像、2 CPU、2 GiB 内存、零 swap，每次从全新隔离产物开始，操作系统文件缓存未强制清空。

本轮保留逐点探测，并将默认 P5 自动模式的直接输入窗口从 20 秒缩到 12 秒。原来的可接受 PTS 仍为目标之后一个采样间隔，即默认 10 秒；保留额外两秒解码余量。第一轮整片中有 133 个合格直接样本落在目标后 2～10 秒，不能把单点容差收窄到连续段的两秒。

短恢复入口先沿用最多 6 格。只有一个完整连续段取得至少 6 格、下一点直接定位仍失败，且实测恢复成本明显高于连续解码每格成本时，才评估扩大到 12 格或 25 格；仍受页面和 300 秒输入上限约束。最近成功预读长度只作为短期尝试顺序提示，不替代新位置的实际验证。完整回退链、提示失效条件和成本规则见[播放链路](../developer/playback.md#倍速缩略图与预缓存)。

实片对照覆盖普通位置、困难段转正常位置、1650 秒与 4980 秒附近，以及已有连续段。除了比较耗时、命令和图片，还分别统计无输出与晚 PTS 拒绝；缩短输入可能让原来的晚 PTS 拒绝变成无输出，不能仅按空跑次数判断收益。实际批次扩大和提示重排的触发结果也需记录，不能把规则已实现当作本片已获得相应提速。

初次实片对照发现了长预读提示的退化：1650～1700 秒的 6 格从 93.028 秒增加到 128.009 秒，时间与像素相同。1650 秒需要 60 秒恢复，1660 秒已可直接定位，1670／1690 秒实际只需 10 秒，但提示使两处都进行了 60 秒预读。修正为任一次直接成功就清除排序提示，且进入预读后始终先试 10 秒，再使用较长提示。不能将“较长预读成功”视为“较短预读必然失败”。

修正版按 P、A 的反序逐组复测，以下各一轮；普通位置、孤立难点和转正常位置另有此前 A 对照。两轮顺序与系统文件缓存均会影响结果，不将单个最好值作为固定提速保证。

| 采样片段 | 第一轮最终代码 A | 第二轮修正版 P | 结果 |
| --- | --- | --- | --- |
| 100～150 秒，6 格 | 6.795 秒 | 6.847 秒 | 均为 7 条命令，耗时相近 |
| 1650～1700 秒，6 格 | 99.622 秒 | 80.737 秒 | 均为 18 条命令，本轮耗时减少约 19%；初始 A 同段为 93.028 秒 |
| 250～490 秒，25 格 | 89.727 秒 | 91.400 秒 | 均为 28 条命令，未观察到稳定收益 |
| 610～740 秒，14 格 | 100.690 秒 | 94.202 秒 | 均为 20 条命令，本轮耗时减少约 6% |

这四组共 51 格均为相同实际 PTS，独立解码后的 RGB 哈希全部一致，无需以不同时间画面估算颜色差异。4980～5000 秒的初始候选对照为 149.851→146.360 秒、3 格同 PTS／像素一致；该组发生在提示修正前，最终代码对该位置的确认来自下面的整片验收。

### 第二轮整片验收

修正版从空诊断缓存单次完成全部 540 格、22 页，生成耗时 **3313.763 秒（55 分 13.8 秒）**，包含恢复和最终拼图。对比第一轮最终代码的 3840.495 秒，少 526.731 秒，约 13.7%。两次使用相同片源、镜像和资源限制；这是一次历史整片对照，操作系统文件缓存及宿主状态未控制，不作为其他设备或多次运行的固定提速保证。

540 格实际 PTS 与第一轮全部相同，采样 PNG 哈希全部相同，22 张最终 JPEG 哈希也全部相同。时间严格递增，偏移仍为 −0.25～+9.875 秒；1650 秒、4980 秒和片尾均通过，没有手动接纳缺失。22 张 JPEG 均通过严格解码与尺寸核对，隔离 ASGI 调用实际图片处理函数全部返回 200、`image/jpeg`，字节哈希一致。该检查覆盖图片交付函数，真实服务认证和清单查询继续由相关回归覆盖。

本片共执行 31 次批次长度决策、85 次预读顺序决策，**短批扩至 12／25 格与提示重排均未触发**。731 条命令、31 个连续段及各采样路径的格数与第一轮相同，不能把本次提速归功于扩大批次或提示重排。这两项规则已接入并通过合成状态与路由测试，其实片收益仍需其他适用片源验证。

实际变化是 365 次直接探测的输入上限从 20 秒缩为 12 秒。同样 142 次未取得合格画面的直接探测，合计耗时从 1089.469 秒降到 722.924 秒，少约 366.5 秒，支持缩短多余读取的方向。其内部无 PTS 次数从 54 增至 118，晚 PTS 被拒从 88 降至 24；全体空 seek 次数也随之从 248 增至 312。这属于截断后的分类变化，不能解释为新增失败，也不能把其余耗时差额归为未触发策略的收益。

连续段实际最多 24 格、输入 272 秒、首目标前置 70 秒、执行预算 544 秒，均未越过原边界。容器正常退出、无 OOM；内存峰值仍达 2 GiB，`memory.events.max` 计数为 20794。内存统计包含文件缓存，不能据此宣称有充足内存余量。

本轮证据保存在本机忽略目录 `output/diagnostics/preview-adaptive-20261022/`：`F-P-final.jsonl`、冻结源码、完整报告、容器记录及独立审计均逐项绑定哈希。修正版 746 项相关回归通过、4 项跳过，Python 静态检查和完整帮助站验证通过。2026-10-23 的独立审计确认整片证据有效；本地挂载的 161 个源码文件与冻结版本匹配，原有 22 页和清单共 23 个文件哈希未变。核对时本地服务容器已停止，因此没有追加在线健康验收；本轮未启动服务或发布新缓存，也未部署 NAS。

## 实施顺序与验收

| 阶段 | 交付与通过条件 | 当前状态 |
| --- | --- | --- |
| 资料与原因边界 | 一手来源、当前成本及未确定根因清楚，候选方案可比较 | 已完成 |
| 隔离原型 | 合成状态／错误时序通过，再对正常段、1650 秒附近、4980～5000 秒比较 A／C；测量 B 的连续解码成本 | 已完成小段对照及 B 的吞吐观测 |
| 策略接入 | 根据证据确定窗口和切换条件，提交、资源与恢复回归通过 | 第二轮 746 项相关测试通过、4 项跳过；跨页流式提交保留后续评估 |

每次对照记录 wall time、CPU、内存峰值、FFmpeg 次数、失败尝试耗时、读取量、区段覆盖及实际 PTS；能取得时记录解码帧数。冷暖缓存、构建和资源限制必须一致，采用串行重复测量。收益需超过波动，且普通片不能出现可重复的性能退化，再进入全片验证；不提前承诺提速倍数。

颜色对照必须使用同一实际 PTS，并区分抖动差异与错误色彩。可在隔离参考中固定抖动，生产转换参数保持原值。增加元数据间断、错误定位、VFR、附带封面、损坏尾部、磁盘失败、中断恢复和播放让行场景；缺图不能复制相邻帧凑齐数量。

新旧完整缓存保持可回退。采样语义或输出像素合同变化时再评估缓存 revision；已有合格图片不能只为计时重复覆盖。实片性能测试必须使用独立诊断缓存，不能把现有成品命中或接纳缺失片尾当作提速结果。NAS 部署、NAS 实片性能及《唐人街探案3》完整验证不包含在本次调研完成状态内。
