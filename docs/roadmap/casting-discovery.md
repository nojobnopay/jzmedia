# 投屏发现后续计划

[开发计划](README.md)

**状态：真机对照与 NAS 主服务迁移已完成，0.30.3 提供 host 部署支持。** 用户于 2026-10-25 恢复本项，要求先比较服务器 DLNA 与小米浏览器全能播放器；随后决定 Linux／NAS 需要自动发现时推荐整个 jzmedia 使用 host，暂不开发发现助手。优先满足电视停在桌面即可接收，不开发手机 App，也不新增电视接收应用。服务器 DLNA 为主路线，小米播放器保留为可选发起播放入口；真实长片、HDR 及字幕选轨扩展仍需分别验证。

本项曾于 2026-10-21 降低优先级；此前手动添加和合成片源验证继续保留为已有证据，不代替本轮两台电视、浏览器及目标部署的验收。

## 已有能力与证据

- 网页投屏由服务器执行 SSDP `MediaRenderer:1` 搜索、电视 HTTP 控制和媒体供给。普通手机浏览器无法直接收发 SSDP 所需的原始 UDP；当前仓库只有网页前端和独立 Android TV 客户端，没有手机原生客户端。[Chrome Direct Sockets 说明](https://developer.chrome.com/docs/iwa/direct-sockets)
- `POST /api/cast/devices` 可接收完整的 DLNA 描述地址，由服务器验证并加入进程内设备列表；投屏面板提供手动输入。此入口没有手机自动发现能力，重启服务后也不保留手动设备。代码位置及接口约定见[播放核心设计](../developer/playback.md#dlna-接收端播放)与[投屏 API](../developer/api.md#dlna-投屏)。
- 2026-10-13，本机 Windows WLAN 可收到一台小米电视的 SSDP 回复，受测 WSL NAT、Docker Desktop 桥接容器和临时 host 容器均未收到；固定 UDP 端口映射也未解决。容器可读取电视描述并调用控制接口，故该环境已定位的缺口是自动发现，不能由此推断所有容器部署均不可投屏。
- 同次试验用临时 jzmedia 实例、隔离数据库和 15 秒合成 MP4，手动注册小米电视后收到 HTTP 206 Range 取流，电视上报 `PLAYING` 和约 3 秒进度，停止命令成功。当时未观察实际声画；该临时实例与数据已清理，后续发行版本已纳入手动注册代码。
- 2026-10-25 的隔离对照阶段，NAS 宿主机及临时 host 网络容器均发现主卧小米与客厅 Redmi 两台 DLNA 接收器，当时桥接容器同类搜索为空。临时容器复用 NAS 基于 0.30.2 的试用镜像，只挂载独立测试目录与夹具脚本；该阶段未改正式服务、配置和媒体库。
- 本轮使用带可见计时和测试音的 180 秒 H.264/AAC 完整 MP4。实际 HTTP 检查覆盖 HEAD、整片哈希、首段／中段／尾段 Range 字节、越界 416、无效取流授权和控制授权；11 项均通过。390px 浏览器模拟中页面可访问、无脚本错误或横向溢出，能列出两台电视；该检查不能代替小米浏览器真机投屏。
- 两台电视均由 NAS 隔离服务从桌面起播；用户逐台确认画面、递增计时和声音，以及暂停、恢复、跳到 90 秒和停止均正常。设备状态回报同步验证了暂停、恢复、跳转后的真实位置和 `STOPPED`。
- 两台电视分别重新起播后，用户确认手机锁屏或关闭测试页约 20 秒，电视仍持续播放且声画正常。日志显示两台电视直接以 HTTP 206 读取 DLNA 媒体，播放器标识均为 Android 9 的 `stagefright/1.2`，未由手机代取。这些结果只覆盖本次合成片基础验收，不扩大为真实媒体库、长时间播放或待机唤醒结论。
- 小米全能播放器使用原生整片 HTTP MP4 页时，用户确认能发现两台电视，逐台声画正常，并分别确认手机锁屏、切应用、退出纯视频页三种情况下均继续播放。日志确认两台电视均直接以 HTTP 206 读取独立浏览器媒体地址；未取得手机浏览器的具体版本号。
- 用户澄清两套控件都曾操作，小米自带投屏可正常发起，但投屏状态下没有暂停等按钮可选。该路径的控制结论是浏览器界面不可用，不能把上方服务器 DLNA 控件的成功归入小米原生控制，也不能据此认定电视或协议不支持暂停。
- 扩展夹具的原生 TS-HLS、双 AAC 音轨 MP4 和外挂 WebVTT 共 15 项 HEAD／Range、完整 VOD 与原生页面检查通过。用户确认两台电视均可通过小米播放器投屏 TS-HLS，声画正常；手机浏览器与两台电视均不能选择第二音轨，本次外挂中文字幕在手机和电视均未显示。双音轨视频的声画未单独确认，不能把无法选轨解释为解码失败；字幕结论仅限本次 WebVTT 与受测入口，不推广到全部字幕。
- 17 条用户现场观察已逐项保存；撤销主夹具浏览器独立取流授权后，HEAD 与 GET 均返回 404。两台电视收尾前只读状态均为 `STOPPED`，未误停其他资源。测试容器及本次临时目录已删除，测试地址不再可用；隔离阶段收尾时，正式容器身份、镜像、启动时间与完整配置摘要均与该阶段基线一致，健康状态与 API 均正常。
- 仓库最终夹具将服务器控制与独立浏览器页分开；对该版本另做 9 项实际 NAS HTTP 复核，覆盖页面隔离、HEAD／Range、空设备清理、授权撤销及日志脱敏，全部通过。此轮复核未搜索或控制电视，使用的独立容器与目录也已删除；不以最终源码复核冒充该版本重新完成真机投屏。
- 后续正式迁移阶段，NAS 主服务已持久使用 host，保留原媒体、数据、用户组、硬件设备、资源限制与观看保护，代理切换到宿主可达入口。当前服务以既有凭据验证 TMDB API 与图片均成功，正式投屏发现接口列出两台电视；外部首页、健康接口和帮助页可访问，host 推荐说明已随静态资源部署。基于原试用镜像仅更新网页与帮助，后端源码一致；已有数据库与停服时队列得到一致备份，保留原镜像和配置可回退。该阶段未发起真实媒体扫描、整理或播放，不以正式服务发现成功替代真实长片验收。

本机电视地址、容器网络与代理测试的易变细节只记录在本机忽略的 `docs/private/project-memory.md`，重新测试时以现场状态为准。

## 后续实现路径

**按已验证结果推进免新增安装的正式方案。** `scripts/fixtures/casting_lan_server.py` 保留为隔离复验入口，不修改正式播放器或生产 API，不挂载真实媒体和数据。服务器控制页与纯浏览器视频页分开，避免将一套控件的结果算入另一条路线；两条路径使用同一合成 MP4，授权相互独立。

服务器 DLNA 已通过两台电视的基础验收并提供完整基本控制，推荐作为主路线。原生 Linux／NAS 的自动发现采用整个主服务 host 部署，保持单服务结构；仓库提供可选 `compose.host.yml`，默认 bridge 配置继续支持普通播放和不依赖组播的部署。暂不开发独立发现助手。host 的端口映射、代理地址、旧 Compose 等价配置及数据保留要求见[部署教程](../getting-started/deployment.md#host-network)；NAS 主服务已另行完成端口、代理、原数据和生产设备发现核验，后续升级继续保留 host 配置。

小米路径可作为可选的发起播放入口，由用户在全能播放器中选择电视；受测 MP4 与 TS-HLS 均能起播，但原生控制、选轨和外挂字幕存在上述限制。视频页提供电视可读取的完整 HTTP 地址，不使用 Blob、MSE、网页换片或禁止远程播放属性；取流不依赖手机 Cookie 或自定义请求头。不以服务器控制面板代替其原生操作，不承诺网页可枚举全能播放器设备或获得稳定状态回调，也不沿用网页自绘字幕可传递的假设。

复杂字幕和音轨选择继续使用已有 jzmedia-tv；如要补齐内置接收器路径，再单独评估服务端选轨或字幕烧录及其成本，不把它们列为本轮已实现功能。不为本轮已验证路径新增手机 App。以后如需手机网页遥控现有 TV App，再评估由 TV 主动连接服务器接收命令；前台接收与电视桌面后台唤起分开验证。Android 手机原生发现仅保留为候选：它可补足 UDP 发现，但会增加手机安装，也不会自动解决电视侧后台启动权限。普通网页及 PWA 不具备该 UDP 能力。[Android DatagramSocket](https://developer.android.com/reference/java/net/DatagramSocket)、[局域网权限](https://developer.android.com/privacy-and-security/local-network-permission)

## 重新启动时的验收条件

以下用于正式集成或部署变化后的复验；本轮通过范围限于合成片与受测设备，不代替真实片源、长播或待机唤醒验收。

1. 两台电视分别开启内置接收并停在桌面，记录自动发现与起播；搜索失败时仅对已取得有效描述地址的设备测试手动添加。
2. 服务器 DLNA 逐台验收实际声画、暂停、恢复、跳到 90 秒和停止；另起一次播放，关闭手机页面后确认持续播放。
3. 小米手机打开简单视频页，逐台验收全能播放器发现、起播、控制及锁屏／切应用／退出网页；结合真实连接 IP、Range 和响应日志区分电视取流与手机代取，日志隐藏完整授权链接。
4. 基础播放通过后再验证原生 HLS、双音轨和外挂字幕。每台分别标记发现、取流与现场声画结果，不能以状态回报或一台成功代替另一台验收。
5. 收尾时仅停止确认仍属于本次夹具的播放；播放 URI 无法确认时跳过，避免误停其他视频。清理本次容器及临时数据，复查正式服务健康；正式 host 网络与代理按部署变更核验，真实片源继续单独验证。

此前后端投屏定向测试、前端测试与浏览器冒烟通过的记录保留；本轮隔离夹具和真实设备结果按上述范围单独验收。剩余字幕、选轨与真实片源兼容改进按使用需求安排，改动时按影响范围重新回归。
